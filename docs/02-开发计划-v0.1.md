# Memory Palace 开发计划 v0.1

> 依据：[Memory Palace 技术方案 v0.1](./Memory-Palace-技术方案-v0.1.md)
> 配套文档：[技术选型评估](./01-技术选型评估-v0.1.md)
> 前提：本地优先单用户 / 全 TypeScript / 云 API + 薄抽象层
> 日期：2026-09-21

---

## 0. 计划总原则

1. **先有测量，再有优化。** Formation / Evolution / Recall 全部是 prompt + 阈值驱动的启发式系统。没有评测集，任何 prompt 改动都是盲改。
2. **Domain 不依赖基础设施。** `packages/core` 里不出现 SQL、HTTP、MCP、厂商 SDK 的类型。三者都通过端口（interface）注入。
3. **每个 Phase 都必须可独立验收。** 验收标准写成可执行的测试，而不是"看起来能用"。
4. **记忆是追加写（append-only）。** 任何"修改一条记忆"的语义都落地为"新增一条记忆 + 一条关系边"，绝不做破坏性 UPDATE。这是 §6 时间模型的工程化落地。
5. **单用户，但绝不假设单用户。** 所有表带 `user_id`，仓储层强制传 `userId`。为多租户预留，不实现。

## 1. 对原方案执行顺序的三处修正

这是本计划与你原方案 §28 路线图的主要差异，请重点确认。

### 修正 1：评测系统从 Phase 8 提前到 Phase 2（最重要）

原路线：

```text
Phase 1 Memory Model → Phase 2 Formation → ... → Phase 8 Evaluation System
```

问题：Formation 的抽取 prompt、Dedup 的相似度阈值、Conflict 的判定策略，都是**必须反复迭代**的参数。把评测放在第 8 位，意味着前 7 个阶段全部在"无法判断改动是好是坏"的状态下开发——而这些恰恰是整个系统最难、最需要迭代的部分。

修正后：

```text
Phase 1 Memory Model + Storage → Phase 2 Evaluation Harness → Phase 3 Formation
```

代价：多花 3-5 天。收益：此后每一次 prompt 调整都有回归保护。

### 修正 2：Memory Model 与 PostgreSQL 存储合并为一个阶段

原方案把 Phase 1（Memory Model）和 Phase 5（PostgreSQL + pgvector）拆开。但 bi-temporal 语义（`valid_from/valid_until` + 事务时间）能否正确表达"2025 用 React、2026 转 Vue、2027 又转回 React"，只有在真实 SQL 上跑时间旅行查询才能验证。纯文档设计会漏掉一半问题。

修正后：Phase 1 = 数据模型 + Drizzle schema + 迁移 + 时间旅行查询测试。

### 修正 3：MCP 只读入口提前到 Phase 3 结束

原方案 MCP 在 Phase 6。但 MCP 是唯一能让真实 Agent（Claude Desktop / Cursor / DSH）用上 Memory Palace 的通道。等到 Phase 6 才第一次真实使用，等于把"Agent 是否真的更了解用户"这个核心问题推到两个月后才回答——而 §26 明确说这才是最该验证的问题。

修正后：Phase 3 结束时暴露一个最小 `memory_recall`（只读），立刻开始 dogfooding；Phase 6 补齐写路径与权限策略。

## 3. 各阶段详细计划

### Phase 0：项目骨架（2-3 天）

**任务**

- pnpm workspaces monorepo，目录结构按 §25 落地：

```text
memory-palace/
├── apps/
│   ├── api/          # HTTP JSON API（供 Web UI）
│   ├── mcp/          # MCP server（stdio，主入口）
│   └── web/          # 记忆管理 UI
├── packages/
│   ├── core/         # 纯 domain：memory / formation / evolution / recall
│   ├── storage-pg/   # Postgres + pgvector 适配器（实现 core 的端口）
│   ├── retrieval/    # semantic / lexical / fusion / ranking
│   ├── llm/          # LLM + Embedding provider 端口与适配器
│   └── shared/       # 类型、Result、错误、config、日志
├── migrations/
└── docs/
```

- tsconfig 项目引用（`composite: true`），让 `core` 无法 import `storage-pg`
- **全项目 ESM（`"type": "module"`，`module: NodeNext`）—— 必须在 Phase 0 定死。** AI SDK 7 是 ESM-only，CommonJS 已被移除。事后从 CJS 迁到 ESM 是纯返工
- **`erasableSyntaxOnly: true` + `verbatimModuleSyntax: true`**，并**禁用 `enum`**（实测 `TS1294` 会拦截）。成本几乎为零，收益是保留未来用 Node 原生直跑 TS 的可能
- **每个包用 `exports` 字段定义公开入口**。这是"Domain 与基础设施解耦"唯一可靠的执行机制——实测越界 import 私有子路径会被编译器拒绝（`TS2307`），靠自觉是拦不住的
- **依赖版本 pin 精确值**（尤其 `typescript: "7.0.2"`，不加 `^`）。TS 7 是刚发布的 Go 原生重写版
- Biome（format + lint 一把梭，替代 ESLint+Prettier 两套配置）
- Vitest + 一个真实 Postgres 的集成测试夹具（testcontainers 或本地测试库 + 事务回滚）
- 本地开发数据库：**用你已装好的 Homebrew PostgreSQL 18 + pgvector 0.8.2**，零 Docker 摩擦；同时提交 `docker-compose.yml`（`pgvector/pgvector:pg18`）作为可复现路径

> **两个已知环境坑，Day 1 就会遇到：**
> 1. pnpm 全局 store 在 `~/Library/pnpm/store`。在受限/沙箱环境下会因 `EPERM` **静默失败**（`pnpm install` 显示成功但没有 `node_modules`）。遇到时加 `--store-dir <可写路径>`。
> 2. `tsconfig` 的 `extends` 里，**相对路径相对于基础配置文件解析**。`rootDir` / `outDir` 必须写在每个子包的 `tsconfig.json`，否则报 `TS6059`。

**验收标准**

- `pnpm dev` 能起 api 与 mcp 两个进程
- `pnpm test` 包含至少一个真实读写 Postgres 的集成测试
- `CREATE EXTENSION vector` 在迁移中成功执行
- 写 ADR：`0001-记忆的不可变与双时态模型.md`、`0002-存储选型.md`、`0003-LLM-Provider-抽象边界.md`

### Phase 1：Memory Model + 存储内核（1 周）

#### 3.1 数据模型决策（对原方案 §5 的关键修正）

原方案把 `supersededBy`、`validFrom`、`validUntil`、`status` 全部放在同一个 `Memory` 行上，同时又提到一张 `memory_versions` 表。这会在第一次"修改记忆内容"时产生歧义：到底是 UPDATE 同一行（丢历史），还是插新行（那 `superseded_by` 指向谁？）。

**建议：记忆行不可变（immutable），版本即行，关系即状态。**

```text
observations        原始经验（Experience），只追加
  id, user_id, content, source_kind, source_ref, agent_id, occurred_at, created_at, metadata

memories            记忆版本，只追加，永不 UPDATE
  id, user_id, type, content, summary,
  confidence, importance,
  valid_from, valid_until,          -- 有效时间：这件事在现实世界中何时成立
  recorded_at, superseded_at,       -- 事务时间：系统何时开始/停止相信它
  status,                           -- 由关系维护的物化投影（active|superseded|archived|disputed）
  origin_observation_id, agent_id, extraction_run_id, metadata

memory_relations    记忆之间的带类型边，只追加
  id, user_id, from_memory_id, to_memory_id,
  kind,                             -- supersedes|contradicts|supports|related_to|derived_from
  reason, created_at, created_by

memory_embeddings   每条记忆版本 × 每个 embedding 模型一行
  memory_id, model, dim, embedding, created_at

entities            id, user_id, canonical_name, kind, aliases, created_at
memory_entities     memory_id, entity_id, role
memory_sources      记忆 → 来源（观测/文档/Agent/用户）的多对多溯源
agent_policies      哪个 agent 可以写哪类记忆、是否需确认
extraction_runs     pipeline 每次执行的可观测记录（成本、耗时、模型、prompt 版本）
```

为什么这样切：

- **不可变行 + 关系边**彻底满足 §6「不能 `UPDATE memory SET content=...`」。
- **双时态**（有效时间 + 事务时间）才能同时回答"你现在用什么技术"和"你当时为什么以为他在用 Vue"。原方案只有有效时间。
- `status` 保留为**物化投影**（查询快），但必须在写关系的同一个事务里更新，并配一个一致性测试防止漂移。
- `memory_embeddings` 独立成表，可以换 embedding 模型重嵌入而不丢旧向量，也支持两模型 A/B。这直接支撑 Phase 2 的评测对比。
- `extraction_runs` 从第一天就记——否则评测失败时无法定位是 prompt、模型还是数据的问题。

**关于"同一 claim"的处理：** 不要在 MVP 引入槽位本体（subject+predicate 的规范化 key），那需要一套 ontology，成本高且脆。改用**决策驱动**方式：ANN 召回同类活跃记忆 → LLM 成对裁决 → 落库。代价是 LLM 调用，收益是无需本体且更鲁棒。槽位表留到 Phase 9 作为性能优化。

冲突裁决的输出空间（这是整个系统最关键的 prompt）：

```text
DUPLICATE   语义等价，仅强化（+confidence，更新 recorded_at）
REINFORCE   部分重叠，补充细节，可合并 content
SUPERSEDE   同一事实的新状态，旧的 valid_until = 新 valid_from，建 supersedes 边
CONTRADICT  互斥但无法判断哪个更新/更可信 → 双双标 disputed，进人工确认队列
COEXIST     不同维度，各自成立（如"喜欢 Rust"与"在用 TypeScript"）
UNRELATED   预筛误召，忽略
```

**关键约束：冲突检测只在同 `type` 的 top-k 近邻里做，不做全表两两比较。** 否则是 O(n²) 的 LLM 调用。

**任务**

- Drizzle schema + `drizzle-kit generate` 迁移（含 `vector(1024)` 自定义类型）
- HNSW 索引（`vector_cosine_ops`）；分词索引用 Postgres 原生 `tsvector` + GIN 起步
- `packages/core` 定义仓储端口（`MemoryRepository`、`ObservationRepository`、`MemorySearchPort`、`EntityRepository`）
- `packages/storage-pg` 实现端口；所有时间旅行查询手写 SQL（Drizzle 的 query builder 表达能力不足时直接用 `sql` 模板）
- 时间表达式解析的**输入接口**先定义（Phase 4 实现）

**验收标准（写成测试）**

1. 插入 React(2025-2026) → Vue(2026-) 后，`asOf=2025-06` 查到 React，`asOf=2026-06` 查到 Vue
2. `asOf` 加上事务时间维度：能回答"在 2026-01 时系统认为用户在用什么"
3. supersede 后旧记忆 `status='superseded'`、`superseded_at` 有值、存在 `supersedes` 边
4. 一致性测试：遍历所有记忆，`status` 投影与关系边推导结果完全一致
5. 同一记忆版本可用两个不同 embedding 模型各存一份向量

### Phase 2：评测 Harness + Golden Dataset（3-5 天）

**为什么必须在 Formation 之前**：抽取 prompt 的第一版必然很差，你需要知道它"差多少、差在哪一类"，而不是凭感觉改二十轮。

**任务**

- Golden Dataset（放 `evals/datasets/`，JSON/YAML，人工标注）：

```yaml
# 抽取集：观测 → 期望记忆
- id: extract-001
  observation: "我最近开始系统学习 Effect-TS。以后你给我讲 TypeScript 的时候，先从整体结构和设计思想讲，再深入 API。"
  expect:
    - { type: goal,       content_contains: ["Effect-TS"], must_have: true }
    - { type: preference, content_contains: ["整体结构", "设计思想"], must_have: true }
  must_not_extract:
    - "用户喜欢 TypeScript"        # 不能过度泛化

# 演化集：已有记忆 + 新观测 → 期望决策
- id: evolve-001
  existing: [{ type: preference, content: "用户喜欢 Java" }]
  observation: "我现在已经不太写 Java 了。"
  expect_decision: SUPERSEDE
  expect: { old_valid_until_set: true, new_valid_from_set: true }
```

- 指标（`pnpm eval` 输出）：

```text
Extraction Precision / Recall / F1
Type Classification Accuracy
Dedup Accuracy          （该合并的合并了、不该合并的没合并）
Conflict Decision Accuracy（6 分类混淆矩阵）
Temporal Accuracy
Recall Precision@5 / Recall@5
Negative Accuracy       （无关查询必须返回空——原方案 Case 4）
Cost per 1000 observations（token 与金额）
Latency p50 / p95
```

- Runner 设计要点：
  - 每个 case 跑在**独立事务**里并回滚，保证可重复
  - 结果落 `evals/runs/<timestamp>.json`，支持 `pnpm eval --compare <runA> <runB>` 出 diff
  - 记录 prompt 版本哈希与模型名，否则结果不可比
  - LLM 调用必须可缓存（按 prompt 哈希），否则迭代一次评测要烧一遍全量 token

**验收标准**

- `pnpm eval` 在空实现上跑出全 0 基线（证明 harness 本身没 bug）
- 在 mock 的"完美实现"上跑出全 1（证明指标方向正确）
- 一次全量评测成本 < $2，耗时 < 5 分钟

### Phase 3：Memory Formation（1.5-2 周）

**Pipeline（对应 §7，但每步独立可测）**

```text
Observation 入库
   ↓ ① 预处理：切分长输入、时间锚定（相对时间 → 绝对时间）
   ↓ ② Candidate Extraction   （LLM + Zod schema，温度 0）
   ↓ ③ Classification         （并入 ② 的同一次调用，省一次往返）
   ↓ ④ Entity Extraction & Resolution
   ↓ ⑤ Dedup                  （ANN 预筛 → LLM 裁决 DUPLICATE/REINFORCE/NEW）
   ↓ ⑥ Conflict Detection     （ANN 预筛同类型活跃记忆 → LLM 裁决四选一）
   ↓ ⑦ Importance / Confidence 评分
   ↓ ⑧ Persistence（单事务：记忆 + 关系 + 实体 + 向量 + status 投影）
   ↓ ⑨ extraction_runs 记录
```

**设计要点**

- ②③ 合并为一次 LLM 调用（一个 schema 里同时给 type 和 content），显著降本降延迟。原方案 §7.1/§7.2 分成两步，工程上不划算。
- **幂等性**：同一条 observation 重复 ingest 不得产生重复记忆。用 `origin_observation_id` + 内容哈希做唯一约束兜底。
- **每一步都是纯函数 + 显式输入输出**，便于单测与在评测里单独打分。不要写成一个 500 行的 `processObservation()`。
- **失败降级**：LLM 调用失败或 schema 校验失败时，observation 必须完整保留并标记 `pending`，可重放。绝不因为 AI 失败而丢用户输入。
- Confidence 的锚点建议（避免模型乱给分）：用户显式声明 0.9-0.98、Agent 行为推断 0.6-0.75、从上下文弱推断 0.4-0.6。把这个 rubric 写进 prompt，而不是让模型自由发挥。
- Importance 同理给 rubric，并允许用户手动覆盖。
- **不要用 Zod 的复杂约束来"逼"模型守规矩。** 实测确认：OpenAI 的 strict 模式**不强制执行** `pattern` / `format` / `minLength` / `minimum`。所以约束要用三段式——**prompt 里明确说明 + 本地 `safeParse()` 校验 + 失败重试**。LLM 返回后**永远必须再校验一次**。
- **抽取阶段的 schema 必须"JSON 友好"**：时间用 ISO string 而非 `z.date()`（Zod 4 的 `z.toJSONSchema()` 对 `date` / `bigint` / `transform` 会抛 `unrepresentable`）。这也意味着 `validFrom` 在领域边界上用 string，在存储层再转。
- **若用 DeepSeek 做抽取**：其 strict schema **只能走 tool calls 且需指向 `/beta` base URL**；普通 JSON mode 官方提示会偶发返回空内容。把这个细节写进 adapter 注释，否则半年后没人记得为什么有个 `/beta`。

**最小只读 MCP（本阶段末交付）**

- 只暴露 `memory_recall` 一个工具，stdio 传输
- 接入 DSH / Claude Desktop / Cursor 中至少一个，开始真实使用

**验收标准**

1. 抽取集 F1 达到首个可接受基线（建议 ≥ 0.75，先测出数再定目标）
2. 同一观察连续 ingest 3 次，`memories` 只增加一次
3. 长输入（>4000 字）能正确切分且不产生碎片化记忆
4. LLM 全失败时 observation 仍在库中且状态为 `pending`
5. 真实 Agent 会话中，`memory_recall` 能返回 Phase 2 里"必须召回"的记忆

### Phase 4：Memory Evolution（1 周）

**任务**

- 把 Phase 3 的⑥裁决落成**事务性**写操作，保证「插入新记忆 / 关闭旧记忆有效期 / 建关系边 / 更新 status 投影」原子完成
- **相对时间解析**：把"最近""以前""上周""去年"锚定为绝对时间。这是 Temporal Accuracy 的主要来源，且极易做错——用独立的、可单测的模块，不要塞进抽取 prompt
- **冲突确认队列**：`CONTRADICT` 与高风险写入进入待确认状态；通过 MCP 工具 `memory_confirm` 与 Web UI 双通道处理
- **Reinforce / 强化**：重复提及应提升 confidence 并更新 `recorded_at`，但不新增记忆
- **归档**：长期未强化且低 importance 的记忆转 `archived`（不删除，可召回但默认降权）

**验收标准**

- 原方案 Case 2（旧记忆被新记忆覆盖）与 Case 3（冲突正确处理）在评测集中通过
- Case 5（时间相关记忆）通过：查询"用户现在用什么技术"与"用户之前用什么技术"返回不同且正确的集合
- 事务测试：在持久化中途注入异常，数据库不留下半写状态

### Phase 5：Recall + Ranking + Context Assembly（1.5 周）

**双路径设计（关键）**

```text
fast 路径（无 LLM，纯 SQL + vector）：目标 p95 < 150ms
  → 向量 ANN + tsvector 词法 + 实体过滤 + 时间过滤
  → RRF 融合 → 阈值过滤 → 直接组装

smart 路径（LLM 参与）：目标 p95 < 2.5s
  → Query Understanding（抽实体 / 时间范围 / task_type / 意图）
  → 多路召回 → LLM rerank → 冲突过滤 → 组装
```

MCP 工具暴露 `mode: "fast" | "smart" | "auto"`，`auto` 默认走 fast，低置信时升级到 smart。

**为什么必须双路径**：Agent 会频繁调用 recall。如果每次都是 2 秒以上，整个 Agent 体验会被拖垮——这是记忆系统最常见的产品化失败原因。原方案 §10 只描述了单条 pipeline，没有延迟预算。

**Ranking（§12 的工程化）**

- 用 **RRF（Reciprocal Rank Fusion）** 做多路融合，优于手调加权和——它不需要在每路分数之间做归一化，鲁棒得多
- 手调加权和作为 RRF 之上的可选精排层，仅在 smart 路径启用
- **必须输出可解释分解**：`{ semantic: 0.9, entity: 1.0, recency: 0.75, rrf: 0.031, final: 0.87 }`。没有这个就无法 debug 召回质量
- **负样本约束**：低于阈值时返回空数组，而不是硬凑 top-k。原方案 Case 4 要求"无关记忆被过滤"——这需要在评测里有负样本，且 prompt/threshold 都以此为目标

**Context Assembly（§13）**

- 入参带 `tokenBudget`（默认 1200），按记忆类型分组，`active` 优先，`superseded` 作为历史上下文并显式标注其有效期
- 渲染时**把时间范围写进文本**（如"用户曾使用 Vue（2026-01 至 2027-03）"），让下游 LLM 能自行做时间推理——这比让 Agent 理解结构化时间字段有效得多
- 同时返回 `format: "text" | "json"`；text 给 LLM，json 给程序化消费
- 保留 §13 的最终形态：`Relevant Facts / Preferences / Current Goals / Past Decisions / Relevant Experiences`

**验收标准**

- `explain` 开关打开时，每条结果返回完整分数分解
- fast 路径 p95 < 150ms（10 万条记忆规模下）
- 负样本查询返回空
- 同一查询在 fast/smart 下的召回差异可量化

### Phase 6：MCP 完整接口 + 权限模型（1 周）

> ⚠️ **依赖包名必须用 v2**：`@modelcontextprotocol/server` / `@modelcontextprotocol/client` / `@modelcontextprotocol/core`（均 2.0.0，对应 spec 2026-07-28）。**不要用 `@modelcontextprotocol/sdk`（1.30.0，已进入 legacy v1）**，也不要用社区版 `fastmcp`（仍依赖 v1）。详见[技术选型评估 §8](./01-技术选型评估-v0.1.md)。

**工具集（注意：工具数量要克制）**

```text
memory_recall    主入口，最常用
memory_remember  主入口，写观测（进 candidate 流程，不直接落记忆）
memory_search    结构化检索，供人/Agent 精确查找
memory_update    人工修正记忆（高风险，需确认）
memory_forget    归档/删除（高风险，需确认）
memory_confirm   处理冲突确认队列
```

**设计要点**

- **工具描述的写作质量决定 Agent 是否会用对**。`memory_recall` 的 description 要明确写"当用户提到个人偏好、历史决定、长期目标时调用"，而不是"检索记忆"。这是 MCP 集成最常见的失败点。
- 不要让 `memory_remember` 直接写入长期记忆——它写 `observations`，由 pipeline 异步形成记忆。Agent 不应该有"直接改长期记忆"的能力（§16 的原则）。
- **写权限策略**：`agent_policies` 决定某 agent 可写哪些 type、是否需用户确认。第一天就做，因为事后补会污染已有数据。
- **高风险操作确认**：`memory_update` / `memory_forget` 走两阶段（预览 + 确认），或在 Web UI 确认
- **多 Agent 命名空间**：记忆全局共享（§29 的愿景），但写入方记录在 `memory_sources` / `agent_id`，可按 Agent 审计
- 同时提供 stdio 与 Streamable HTTP 两种传输：stdio 给本地 Agent，HTTP 给远程/容器化 Agent

**验收标准**

- 两个不同 Agent（如 DSH + Claude Desktop）接入并各自成功读写
- Agent A 的写入能在 Agent B 的会话中被 recall 到（验证 §29 的核心愿景）
- 标记为需确认的写入不会自动生效
- 所有工具在 schema 校验失败时返回可读错误而非崩溃

## 4. 风险登记册

| # | 风险 | 影响 | 缓解措施 |
|---|---|---|---|
| R1 | LLM 结构化抽取不稳定，偶发 schema 失败或过度泛化 | 高 | 强制 JSON schema 约束输出 + 温度 0 + **本地 `safeParse()` 兜底**（provider 的 strict 模式不保证值级约束）+ 校验失败重试 + `must_not_extract` 负向评测用例 |
| R2 | 自造评测集自我验证，指标虚高 | 高 | Golden set 从真实会话采集；先只测硬约束（"必须召回"）；标注者与实现者分离（隔天再标） |
| R3 | 冲突检测 LLM 调用成本/延迟爆炸 | 中 | 限定同 type 的 ANN top-k 预筛；裁决结果按 (新记忆, 旧记忆) 哈希缓存 |
| R4 | Recall 塞入过多记忆，反而污染 Agent 上下文 | 高 | tokenBudget 上限 + 分数阈值 + 空结果优先 + 负样本评测；把"返回空"视为正确行为 |
| R5 | 隐私：云 LLM/Embedding 会把记忆原文外发 | 高 | provider 可替换；提供本地 embedding 选项（Ollama / transformers.js）；敏感字段标记；默认零遥测；导出/删除能力完备 |
| R6 | 纯 TS 在数据分析/实验上不如 Python | 低 | 评测 harness 保持 TS + SQL；需要探索性分析时让 Python **只读**同一个 Postgres。读侧不受语言约束，且不在写路径上 |
| R7 | 范围蔓延成"第二个笔记应用/聊天机器人" | 中 | 严守 MVP 边界；Web UI 只做记忆管理；§23 的"暂时不做"清单作为明确护栏 |
| R8 | embedding 模型升级导致全量重嵌入 | 中 | `memory_embeddings` 按模型分行存储；支持后台渐进重嵌入与双模型 A/B |
| R9 | 单用户假设被打破时数据库返工 | 中 | 所有表带 `user_id` + 仓储层强制传参；不实现多租户，但迁移路径已留 |
| R10 | 记忆越积越多后 recall 质量下降 | 中 | archived 状态降权；importance 衰减；定期评测集回归监控 |
