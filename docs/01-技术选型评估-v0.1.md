## 1. 评估方法与约束

选型基于四条约束（你的决策）：

1. **本地优先、单用户**：无需多租户、计费、复杂鉴权。部署复杂度直接决定这个项目能不能长期活下去。
2. **全 TypeScript**：语言单一化，降低个人维护成本。
3. **云 API + 薄抽象层**：不绑定厂商，但也先不承担本地模型的运维成本。
4. **系统本身要轻**（§24 原话）：不为"AI Agent"这个标签强行引入框架。

评估原则：**每一层都先问"能不能用更少的东西解决"**。Memory Palace 的难点在 §27 已经点明——是 Formation / Evolution / Recall 的智能，不是基础设施。基础设施应该尽量无聊。

## 2. 语言：TypeScript（确定）

### 为什么

1. **MCP 官方只有 TS SDK 是"同构"的。** 你的 Agent 生态（Cursor / Claude Desktop / DSH）本身就消费 TS 类型的 MCP 客户端。实测你本机的 DSH 源码 `packages/mcp/mcp-client/src/transport.ts` 直接 `import { StdioClientTransport } from '@modelcontextprotocol/client/stdio'`——写 TypeScript 意味着 Memory Palace 的协议类型和消费方是同一套。
2. **结构化输出的最佳路径在 TS。** Formation pipeline 的核心是"让 LLM 返回严格符合 schema 的 JSON"。Zod 4.6.5 + AI SDK 7 的 `generateObject` 是目前最成熟的组合，且 Zod schema 可以同时用作运行时校验、TS 类型、MCP 工具入参 schema（三者一份定义）。这在 Python 侧需要 Pydantic + 多套胶水。
3. **原方案的数据结构已经是 TypeScript。** §5 的 `interface Memory` 就是 TS。换语言等于把已完成的领域建模重做一遍。
4. **单语言覆盖全栈。** `core` / `api` / `mcp` / `web` 共享类型，改一个字段编译器告诉你所有受影响的地方。对单人项目这是最大的效率来源。
5. **领域复杂度不在数值计算。** Formation/Evolution 本质是 prompt 编排 + 事务正确性 + 检索融合，不是模型训练。Python 的 ML 生态优势在这里几乎用不上。

### 反方案：Python（否决）

反对意见是合理的：Python 在**评测、数据分析、实验迭代**上确实更强（pandas / notebooks / ragas / scikit-learn）。

但它被三点抵消：

- **写入路径不需要 Python。** 评测 harness 用 TS + SQL 完全够用（跑查询、算 P/R、出报告）。真正的探索性分析可以**只读**同一个 Postgres——读侧不受写侧语言约束。这一点很关键：**你不需要在写路径上做语言妥协，就能拿到 Python 的分析能力。**
- **双语言的真实成本被低估。** 两套依赖管理、两套部署、schema 定义漂移、类型无法共享、调试跨进程。对单人项目这是持续性税。
- **MCP 集成要绕路。** Python MCP SDK 存在，但和你的 Agent 生态类型不同构。

**结论：全 TS，Python 仅作为只读分析工具按需引入，永不进入写路径。** 这个折中同时拿到两边的好处。

## 3. 运行时：Node.js 24 LTS（确定）

本机已装 **Node 24.21.0**。核实：Node 24.x 是当前 **Active LTS**（维护期至 2026-10-20，EOL 2028-04-30）；Node 22.x 已进入 Maintenance LTS；Node 26.x 是 Current，2026-10-28 转 LTS。

### 为什么是 24 而不是 26

24 是 Active LTS 而 26 还是 Current。基础设施跑 LTS 是默认正确选择。等 26 转 LTS 后再评估升级。

### 反方案：Bun / Deno（否决）

Bun 1.4.2、Deno 2.9.7 都确实可用，且 `pgvector` 0.3.0 明确支持 deno-postgres 与 Bun SQL。

否决理由：

- Bun 的原生 `Bun.SQL` 会把数据库层**锁死在 Bun 上**，与"保持轻、保持可迁移"冲突。
- 没有找到独立的、生产规模的 Postgres 负载基准（研究未能确认）。
- MCP stdio server 依赖子进程信号处理、stdout 协议纯净性、退出语义——这些是 Node 上被验证过无数次的路径。**基础设施层应该选最无聊的选项。**
- Docker 基础镜像、CI、原生模块（`pg`）生态都最成熟。

### 关于 Node 原生 TypeScript 支持（重要细节，且有实测反转）

Node 24 的原生类型擦除已 **Stable**（v24.12.0 起），看似可以"直接 `node foo.ts`，不需要构建"。实测结论比预期乐观：

- ✅ **它确实能跨 pnpm workspace 符号链接工作**（含传递依赖 `api → core`）。原因是 pnpm 的 `node_modules` 里只是符号链接，真实文件在 `node_modules` 之外，因此不触发"TS in node_modules"限制。
- ❌ 但只支持 **erasable syntax**——`enum` 会报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。
- ❌ **读不到 `tsconfig` 的 `paths`**。
- ❌ 文件若**物理上位于** `node_modules` 内则失败（`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`）。

**建议策略：仍然用 `tsx` 做开发运行**，但理由是"更宽容"而非"唯一可行"——`tsx` 4.23.15 实测能处理符号链接传递导入、`enum`、`paths` 全部情况，且是 Node 官方文档推荐的完整 TS 方案。

```text
开发运行   tsx 4.23.15          （最宽容，官方推荐）
类型检查   tsc -b --noEmit      （TS 7，极快）
生产构建   tsdown 0.23.0        （显式声明支持 TS ^5||^6||^7）
编码约束   erasableSyntaxOnly   （保留 Node 原生直跑的退路）
```

> ⚠️ **不要用 `tsc -b` 做产物 emit。** TS 7 在 `--build` 模式的**声明文件打印环节有未修复的 panic**（[TypeScript#63865](https://github.com/microsoft/TypeScript/issues/63865)，7.0.2 仍可复现，标记 Needs Investigation）。本项目实测的干净构建是通的，但增量重构建这条路径最不成熟——**用 `tsc -b --noEmit` 只做类型检查，产物交给 `tsdown`**。这既规避了 bug，也让构建更快。
>
> `tsup` 8.5.1 已停滞（2025-11）且滞后于 TS 7，`tsdown` 提供官方迁移路径。

> 注：**TypeScript 7 是 Go 原生编译器重写**（代号 Corsa，即原 `tsgo`）。TS 6.0 是最后一个 JS 编译器（2026-03-23 稳定），TS 7.0 于 2026-07-08 稳定并"结构上等价"于 6.0 的类型检查，速度提升 7.7–11.9×、内存降 6–26%。对全新项目是好消息，但有三个必须知道的变化：
>
> 1. **一批配置项被移除（6.0 弃用 → 7.0 硬报错）**：`target: es5`、`downlevelIteration`、`moduleResolution: node/node10`、`module: amd/umd/systemjs`、**`baseUrl`**、`outFile`、`esModuleInterop: false`。**`baseUrl` 被移除意味着路径别名只能用 `paths`（不带 baseUrl）或 package `exports`** —— 这也再次支持了"用 `exports` 定义包边界"的做法。
> 2. **新的默认值**：`strict: true`、`module: esnext`、**`rootDir: "./"`**、**`types: []`**。后两个要特别注意：`rootDir` 的默认值正是 §11 那个 `TS6059` 坑的成因；`types: []` 意味着 **`@types/node` 必须显式写进 `"types": ["node"]`**，否则 `process` / `Buffer` 全部报未定义。
> 3. **`typescript-eslint` 8.70.0 仍声明只支持 `< 6.1.0`**，即**未声明兼容 TS 7**。这正是选择 Biome 的一个额外理由（Biome 自带 Rust 解析器，完全不依赖 TS API，天然不受影响）。若将来确实需要 typescript-eslint，微软的做法是别名并存：`"typescript": "npm:@typescript/typescript6@^6.0.2"` + `"@typescript/native": "npm:typescript@^7.0.2"`。
>
> 另外：**TS 7 在 7.1 之前没有稳定的编程式 API**。这会影响依赖 TS API 的工具，例如 **Vitest 的 `--typecheck`**（需要上面的 TS 6 别名才能用）。普通测试不受影响。

## 4. HTTP 框架：Hono（建议）

两者都有 MCP v2 官方中间件（实测均存在）：`@modelcontextprotocol/hono@2.0.0`、`@modelcontextprotocol/fastify@2.0.0`。所以这不是"能不能用"的问题，是取舍。

| 维度 | Hono 4.13.8 | Fastify 5.12.5 |
|---|---|---|
| 体积 / 心智负担 | 极小，API 极简 | 较大，插件体系 |
| 类型体验 | TS-first，路由类型推导优秀 | 良好，但依赖装饰器式扩展 |
| 生态 | 较小但够用（zod-openapi、cors、logger） | **成熟丰富**（swagger、rate-limit、under-pressure、metrics） |
| 可移植性 | Node / Bun / Deno / Workers 全支持 | 主要 Node |
| MCP HTTP 中间件 | 官方 | 官方 |

**选 Hono 的理由**：本地优先单用户场景下，**HTTP API 不在关键路径上**——主入口是 MCP stdio。既然 HTTP 层是次要的，就选最小的那个：少写配置、少维护、少升级。同时它保留了"未来托管成多用户服务"的可移植性，不需要重写。

**什么时候改选 Fastify**：如果你确定要做 Web UI 且需要 OpenAPI 文档生成、限流、健康探针等成套插件。这些 Hono 也能做，但要自己攒。

> **不要在这个选择上花超过 10 分钟。** 两者差别远小于你写 Formation prompt 的质量差别。HTTP 层应该在 200 行以内。

## 5. 数据库：PostgreSQL 18 + pgvector（确定）

原方案 §17/§19 的判断是对的，直接采纳。本机实测：**PostgreSQL 18.3 已安装，pgvector 0.8.2 扩展文件已就绪**。

### 为什么这个组合是对的

1. **bi-temporal 需要真正的 SQL。** "2025 用 React / 2026 转 Vue / 2027 转回 React"这类查询需要范围条件、窗口函数、`DISTINCT ON`、CTE、生成列。这是关系模型的强项，也是本项目的核心难点。
2. **向量只是众多检索信号之一。** 如你 §11 和 §27 所说，语义检索只是 Recall 的一路。为一个"一路信号"引入独立向量数据库，等于把一致性问题翻倍。
3. **事务性至关重要。** "插入新记忆 + 关闭旧记忆有效期 + 建关系边 + 更新 status 投影"必须原子完成。跨系统做不到。
4. **pgvector 0.8.2 已支持 `halfvec` / 量化**，10 万级规模绰绰有余。

### 反方案 1：SQLite + sqlite-vec 0.1.9（否决）

对单用户本地产品很有吸引力（零依赖、单文件）。但放弃的东西太多：范围类型、窗口函数、JSONB 操作符、生成列、`tsvector` 全文检索、真正的并发写。而 bi-temporal 模型**高度依赖**这些。否决。

### 反方案 2：PGlite（WASM 内嵌 Postgres）0.5.8（**重要，值得了解**）

`@electric-sql/pglite` 能在进程内跑真正的 Postgres（含 pgvector），理论上可以做到"零外部依赖、单进程内嵌"。这对本地优先产品的分发体验是巨大诱惑——用户不需要装 Postgres，不需要 Docker。

**但当前否决，原因是进程模型冲突：**

MCP 的 stdio 传输意味着**每个 Agent 会话会 spawn 一个独立的 server 进程**。多个并发会话 = 多个进程 = 多个 PGlite 实例操作同一个数据文件 → **数据损坏风险**。

PGlite 只有在"**有且仅有一个长驻进程持有数据库**"时才安全。而 MCP 的 stdio 模型天然不是这样。

**这条路径在什么条件下会重新打开：** 如果未来 Memory Palace 改为**单一长驻 HTTP 进程**（MCP over Streamable HTTP，所有 Agent 都连它），那么 PGlite 就变得可行，且能带来极佳的分发体验。

**因此架构上必须保留这个可能性：** 仓储层严格依赖 `packages/core` 定义的端口接口，SQL 尽量限制在 `packages/storage-pg` 内，不要在业务代码里散落 SQL。这样未来换 PGlite（或加一个 SQLite 适配器）只是新增一个 adapter，而不是重写。

### 反方案 3：独立向量数据库（Qdrant / Chroma / Weaviate）（否决）

引入第二个存储系统，就引入了两套备份、两套一致性、两套运维、两套版本升级。而收益只是"向量检索快一点"——在一个 10 万级记忆、单用户的场景里毫无意义。**这恰恰是你 §11 想避免的"RAG 思维"。**

### 反方案 4：Neo4j / 图数据库（同意原方案 §18 否决）

§18 的论证已经完整：第一阶段上 Graph DB 增加部署、同步、查询、运维四重复杂度，而图关系可以先在关系模型里表达。采纳，并把 §18 的结论升级为一条架构纪律：

> **Graph 是一种查询模式，而不是一种存储选型。** 等到关系检索成为**实测瓶颈**（而不是想象中的瓶颈），再做 Graph Projection。

### 本地开发数据库策略（基于实测环境）

| 用途 | 方案 | 说明 |
|---|---|---|
| 日常开发 | **Homebrew PostgreSQL 18.3 + pgvector 0.8.2** | 已装好，零 Docker 摩擦，直接可用 |
| 可复现 / 分发 | `docker-compose.yml`，镜像 `pgvector/pgvector:pg18` | **注意：本机 Docker daemon 当前未运行**，需要先启动 Docker Desktop |

> 实测确认：PG 18 与 pgvector 0.8.2 已装，但 **Docker daemon 未运行**（`~/.docker/run/docker.sock` 不存在），且 Postgres 服务未启动（`pg_isready` 无响应）。Day 1 需要 `brew services start postgresql@18`。

## 6. 数据访问：Drizzle ORM（确定）

| 方案 | 版本 | 评价 |
|---|---|---|
| **Drizzle ORM** | 0.45.2 + drizzle-kit 0.31.10 | ✅ **选它** |
| Prisma | — | 否决，见下 |
| Kysely | — | 优秀但只覆盖查询，schema/迁移要另配 |
| postgres.js / pg 裸用 | 3.4.9 / 8.23.0 | 迁移手写成本过高 |

**选 Drizzle 的理由：**

1. **pgvector 原生支持。** Drizzle 的 `pg-core` 直接提供 `vector()` 自定义类型。而实测确认：**Prisma 的迁移引擎无法创建 pgvector 索引，必须写 raw SQL 迁移绕过**——这是一个明确的摩擦点。
2. **SQL-first，不挡路。** 本项目的核心查询（时间旅行、混合检索、RRF 融合）用查询构建器表达不了，必须手写 SQL。Drizzle 允许你在任何地方用 `sql` 模板嵌入原生 SQL，且仍保有类型。Prisma 的抽象层会在这里持续对抗你。
3. **schema 即 TS 代码，迁移可 diff。** `drizzle-kit generate` 产出可 review 的 SQL 迁移文件——对 bi-temporal 这种必须逐条检查 DDL 的场景很重要。
4. **无代码生成步骤。** Prisma 需要 `generate` 且历史上带来引擎体积问题（其 Rust-free client 已改进，但 Drizzle 从设计上就没有这一步）。

**驱动层**：`pg`（node-postgres）8.23.0 + `pgvector` 0.3.0。node-postgres 是最久经考验的驱动；`pgvector` 包提供 `toSql()` 做向量序列化。`postgres.js` 3.4.9 是合理备选（更快、API 更现代），但不是必要优化。

**纪律**：所有 SQL 只出现在 `packages/storage-pg`。`packages/core` 里不能出现任何 Drizzle 类型——领域层只认端口接口。这是 §5 PGlite 路径能保留的前提。

## 7. LLM / Embedding 抽象层（建议）

生态现状（实测版本）：
- `ai`（Vercel AI SDK）**7.0.107**
- `@ai-sdk/openai` 4.0.71 / `@ai-sdk/anthropic` 4.0.58 / `@ai-sdk/deepseek` 3.0.49 / `@ai-sdk/openai-compatible` 3.0.53

### 推荐：AI SDK 做实现，自建端口做边界

```ts
// packages/llm/src/ports.ts —— 领域层只认这些
export interface LlmPort {
  generateObject<T>(req: {
    schema: ZodType<T>
    instructions?: string      // 注意：AI SDK 7 已把 system 改名为 instructions
    prompt: string
    model?: ModelRef          // 允许按任务指定模型
    temperature?: number
  }): Promise<{ value: T; usage: TokenUsage; modelId: string; promptHash: string }>
}

export interface EmbeddingPort {
  embed(texts: string[]): Promise<Float32Array[]>
  readonly dim: number
  readonly modelId: string
}
```

> **AI SDK 7 的两个硬性约束（会传导到整个项目）：**
>
> 1. **ESM-only，且要求 Node ≥ 22。** CommonJS 已移除。因此**整个项目必须从一开始就是 ESM**（所有 `package.json` 加 `"type": "module"`，`tsconfig` 用 `NodeNext`）。这必须在 Phase 0 就定死——事后从 CJS 迁移到 ESM 是纯粹的返工。好消息：我们本来就是全新项目，成本为零。
> 2. **v7 有一批重命名**：`system`→`instructions`、`onFinish`→`onEnd`、`stepCountIs`→`isStepCount`、`experimental_telemetry`→`telemetry`。另外结构化输出的推荐写法已从 `generateObject` 变为 `generateText` + `output: Output.object({ schema })`，结果读 `result.output`。**新代码直接用 `Output.object`。**
>
> AI SDK 的 major 迭代节奏约**每年 2 次**（4.0 → 5.0 → 6.0 → 7.0）。这正是"必须有自己的端口层"的最强论据——否则每半年被 rename 潮扫一遍。

### ⚠️ 结构化输出的真实可靠性（影响风险 R1 的缓解方案）

研究确认了一个容易被忽略的事实：**provider 的"strict schema"并不保证值级约束。**

| Provider | 约束能力 | 关键限制 |
|---|---|---|
| OpenAI | `json_schema` + `strict: true` | 根必须是 object；所有属性必须 `required`；`additionalProperties: false`；**`pattern` / `format` / `minLength` / `minimum` 不被强制执行** |
| Anthropic | 结构化输出 2026-02-04 GA（Sonnet/Opus/Haiku 4.5） | 支持较复杂 schema |
| DeepSeek | 仅 JSON mode；**strict schema 必须走 tool calls 且要指向 `/beta` base URL** | 官方文档提示 JSON mode 偶尔返回空内容；strict 子集不含 `minLength`/`maxItems` 等 |

**这直接改变工程实践：**

1. **永远不要相信 provider 的 strict 模式能替代本地校验。** 拿到结果必须 `schema.safeParse()`——数值范围、字符串长度、正则这些约束只有本地校验才真正生效。
2. **不要在 Zod schema 里塞复杂约束然后指望模型遵守。** 约束应该用"prompt 里明确说明 + 本地校验 + 失败重试"三段式，而不是只靠 schema。
3. **如果抽取用 DeepSeek**，要么接受 JSON mode 的偶发空返回并做重试，要么显式配置 `/beta` 端点走 strict tool calls。**这个细节必须写进 `packages/llm` 的 DeepSeek adapter 注释里**，否则半年后没人记得为什么有个 `/beta`。
4. **Zod 4 自带 `z.toJSONSchema()`**，不需要 `zod-to-json-schema` 依赖。注意默认输出 draft-2020-12，且对 `date` / `bigint` / `map` / `set` / `transform` 会抛 `unrepresentable`——所以**传给 LLM 的 schema 要用"纯 JSON 友好"的类型**（时间用 ISO string 而不是 `z.date()`）。这条会实际影响 Memory schema 的定义方式。

**为什么必须有这层端口，而不是领域代码直接 `import { generateObject } from 'ai'`：**

1. **AI SDK 处在 v7，major 版本迭代频繁**（v5 → v7 在一年多内）。把它挡在端口后面，升级只改一个 adapter。
2. **评测 harness 需要 mock。** Phase 2 的评测要在**无网络、零成本**下跑通（先用 mock 验证"完美实现得满分、空实现得零分"）。没有端口这做不到。
3. **prompt 哈希缓存是评测可行性的前提。** 不缓存的话，一次全量评测就烧一遍全量 token，你就不敢频繁跑评测——而那正是这个项目最需要的东西。
4. **成本可观测。** `TokenUsage` 必须在端口返回，否则"每次抽取多少钱"无法回答（开发计划 Phase 2 的指标之一）。
5. **按任务选模型。** 抽取可用便宜模型（如 DeepSeek），冲突裁决可能值得用更强的模型。端口化后这是一行配置。

**不要用 LangChain.js。** 它解决的问题（链编排、多 provider、记忆抽象）你已经用几百行显式 pipeline 更清楚地解决了，而它带来的是抽象泄漏和升级痛苦。§24 的"不需要强行引入框架"在这里尤其适用。

> 顺带：你 DSH 的默认模型是 `deepseek-flash`，且 `@ai-sdk/deepseek` 存在。抽取这类高频低难度任务用 DeepSeek 性价比很高。

**待定（需要你决策，见 §13）**：具体 embedding 模型与维度。这同时影响成本、隐私和 `vector(N)` 的 N。

### 与 DSH 对接的具体配置（实测自 DSH 源码）

DSH 的 MCP 客户端配置 schema（`packages/mcp/mcp-client/src/index.ts`）支持两种传输：

```ts
// stdio 形态
{ transport: 'stdio', serverName: 'memory-palace', command: 'node',
  args: ['/path/to/memory-palace/apps/mcp/dist/index.js'],
  env: {}, cwd: '', toolCallTimeoutMs: 60000, failOnStartupError: false }

// Streamable HTTP 形态
{ transport: 'streamable-http', serverName: 'memory-palace',
  url: 'http://127.0.0.1:8787/mcp', headers: {} }
```

三个实测细节会直接影响设计：

1. **工具名会被命名空间化**为 `mcp__<serverName>__<rawName>`，且 `serverName` 必须匹配 `[A-Za-z0-9_-]{1,32}`。所以你的原始工具名要短。
2. **`maxInstructionBytes` 默认 32768**——server instructions 有 32KiB 上限。你 §13 那种"Memory Context 分类模板"如果塞进 instructions 会超限，**应该放在工具返回值里，而不是 server instructions**。
3. **`toolCallTimeoutMs` 默认 60000**。所以"慢"不会撞硬超时，但让 Agent 等 2 秒以上会显著拖慢体感。这从另一个角度支持了开发计划 §5 的 **fast/smart 双路径**设计——**延迟预算不是理论洁癖，是 MCP 集成的实际约束。**

> 生态判断：MCP 仍是主导标准（2025-12 捐给 Linux Foundation 的 Agentic AI Foundation，10,000+ 公开 server，ChatGPT / Cursor / Copilot / VS Code 均支持）。A2A 是 agent 间通信的**互补层**，不是替代品。选 MCP 是安全赌注。

## 9. 检索与排序

> 全部方案已在本机真实 Postgres 18.3 + pgvector 0.8.2 上**实测验证通过**（见 §12）。以下是已确定的架构决策。

**融合策略：RRF（Reciprocal Rank Fusion），而非手调加权和。**

你 §12 提的加权评分公式（`α×Semantic + β×Importance + ...`）问题在于：**各路分数的量纲不同且分布随查询漂移**，权重几乎无法稳定调好，且换一个 embedding 模型就要重调。

RRF 只用**排名**不用分数，天然免归一化：

```text
RRF(d) = Σ_routes  1 / (k + rank_route(d))        // k 通常 60
```

建议：**RRF 做主融合，手调加权和作为 smart 路径上的可选精排层**。这样既保留你 §12 的可解释性目标，又不把系统稳定性押在权重上。

**强制要求：输出分数分解。** 每条召回结果必须能返回 `{ semantic: …, lexical: …, entity: …, recency: …, rrf: …, final: … }`。没有这个，召回质量下降时你无法定位原因——这是记忆系统最容易变成"玄学调参"的地方。

**强制要求：允许返回空。** 低于阈值就返回空数组。你 §26 的 Case 4（无关记忆被过滤）本质上要求系统具备"承认不知道"的能力。如果实现上永远硬凑 top-k，这个能力永远不会出现。**"返回空"必须被当作正确行为来设计和评测。**

### TypeScript 7 实测结论（本机搭真实脚手架验证，非文档推测）

因为 TS 7 是刚发布的重写版本（Go 原生编译器），我在本机**实际搭了一个 pnpm workspace + composite 项目引用的 monorepo 并跑通**，结论如下：

| 验证项 | 结果 |
|---|---|
| TS 7.0.2 `tsc --build` + `composite` + 项目引用 | ✅ 通过，按引用顺序先建 `a` 再建 `b` |
| `tsbuildinfo` 增量构建 | ✅ 通过，二次构建零输出（正确跳过） |
| 声明文件产出（`.d.ts` + `.d.ts.map`） | ✅ 正常 |
| 产出 ESM 在 Node 24.21.0 上运行 | ✅ 通过 |
| 跨包类型安全（`a` 的联合类型在 `b` 中被校验） | ✅ 通过，`TS2322` 正确报错 |
| `exports` 边界（`b` 尝试 import `a/src/index.ts` 私有子路径） | ✅ 被拒绝，`TS2307` |
| `erasableSyntaxOnly` 拒绝 `enum` | ✅ 通过，`TS1294` |
| pnpm workspace 符号链接解析 | ✅ 正常 |

**三条由此确定的实践：**

1. **TS 7 可以放心用于全新项目**，`tsc --build` 的 monorepo 能力完好。但仍建议 **pin 精确版本**（`"typescript": "7.0.2"`，不加 `^`）。
2. **`erasableSyntaxOnly: true` 从第一天就开。** 实测它确实拒绝 `enum`（`TS1294`），代价是多写一点 `as const` 联合类型；收益是始终保留"未来用 Node 原生直跑"的退路。**这个约束是免费的，但事后补要改很多代码。**
3. **用 `exports` 字段把包边界变成硬约束。** 实测私有子路径 import 会被拒绝——这意味着 `packages/core` 想越界访问 `storage-pg` 的内部实现时，编译器会直接拦住。这是"Domain 与基础设施解耦"这条原则**唯一可靠的执行机制**（靠自觉和 code review 是拦不住的）。

### ⚠️ 实测发现的两个环境坑（会浪费你半天，先说）

1. **pnpm 的全局 store 在 `~/Library/pnpm/store`**。实测在受限环境下会因 `EPERM` 无法创建 symlink 而**静默失败**（`pnpm install` 看起来成功，实际没有 `node_modules`）。如果你在沙箱/CI/容器里遇到"install 成功但依赖不存在"，加 `--store-dir` 指向可写路径即可。
2. **`tsconfig` 里 `extends` 的相对路径是相对于*基础配置文件*解析的，不是相对于子配置。** 实测中我把 `rootDir: "src"` 放在根 `tsconfig.base.json`，子包继承后 `rootDir` 被解析成根目录的 `src`，导致 `TS6059`（文件不在 rootDir 下）。**`rootDir` / `outDir` 这类相对路径必须写在每个子包的 `tsconfig.json` 里。** 这个坑几乎每个 TS monorepo 新手都会踩。
3. **pnpm 的严格依赖解析**：只有在自己 `package.json` 里声明过的包才能 import。实测从没有声明的包里 import 会 `ERR_MODULE_NOT_FOUND`。这是**特性不是 bug**——它防止隐式依赖，但要求你在 monorepo 里显式声明每个跨包依赖。
4. **TS 7 的 `types` 默认值是 `[]`**（不再是"自动加载所有 `@types/*`"）。所以每个 Node 侧的子包都必须写 `"types": ["node"]`，否则 `process` / `Buffer` / `setTimeout` 全部报未定义。这个默认值变化很容易让人以为是 `@types/node` 没装。

## 12. 本机实测验证（数据模型 + 检索层）

为了不在流沙上做计划，我在本机**起了一个真实的 PostgreSQL 18.3 + pgvector 0.8.2 实例**（workspace 内自包含、独立端口），把开发计划 §3.1 的数据模型和 §5 的检索设计**实际跑了一遍**。结论：**模型和检索方案都成立**。

### 12.1 双时态模型验证通过

灌入原方案 §6 的经典场景（2025 React → 2026 Vue → 2027 又用回 React，含有效时间与事务时间）：

**① 有效时间查询（"用户在某时刻用什么"）**

| as_of | 答案 |
|---|---|
| 2025-06 | 用户使用 React |
| 2026-06 | 用户使用 Vue |
| 2027-06 | 用户使用 React |

**② 双时态查询（"在事务时间 T 时，系统【当时】相信用户在用什么"）**——这是原方案只有 `valid_from/valid_until` 时**无法回答**的问题：

| 有效时间 | 相信时刻 | 系统当时的判断 |
|---|---|---|
| 2025-06 | 2025-06 | 用户使用 React |
| 2025-06 | 2026-06 | （当时无记忆） |
| 2026-06 | 2026-06 | 用户使用 Vue |
| 2027-06 | 2027-06 | 用户使用 React |

第二行是关键：到 2026-06，系统已经知道 React 那段结束了，所以对"2025-06"不再给出断言。**这正是"双时态"相对"单时态"多出来的表达能力**，也是"你当时为什么以为他在用 Vue"这类问题可答的前提。

**③ 演化链重建（回答"你之前为什么从 React 转到 Vue"）**——用递归 CTE 沿 `supersedes` 边回溯：

```text
depth  content          from_       until_      status
  2    用户使用 React    2025-01-01  2026-01-01  superseded
  1    用户使用 Vue      2026-01-01  2027-03-01  superseded
  0    用户使用 React    2027-03-01  至今        active
+ 转移原因：'用户表示已转用 Vue' / '用户表示又用回 React'
```

注意 2027 的 React 是**独立的第三个版本**，而不是第一条的延续——这正是你要的语义（能区分"回到过去的状态"与"一直在用"）。

**④ 数据库层强制互斥（不靠应用代码）**——加 `slot_key` 后用 GiST 排他约束，实测重叠插入被拒绝：

```sql
ALTER TABLE memories ADD CONSTRAINT no_overlapping_slot
  EXCLUDE USING gist (user_id WITH =, slot_key WITH =,
    tstzrange(valid_from, COALESCE(valid_until,'infinity'::timestamptz)) WITH &&)
  WHERE (slot_key IS NOT NULL);
-- 实测插入重叠区间 → ERROR: conflicting key value violates exclusion constraint
```

> 这说明：**"同一槽位的记忆不能同时有效"这条业务规则可以由数据库保证**，而不是靠每个写入路径自觉。即使 MVP 不走槽位本体（见开发计划 §3.1），这个约束也可以作为 Phase 9 的低成本升级点——**现在就把它当作一条设计纪律记下来。**

**⑤ `status` 物化投影漂移检测**——实测 `status` 字段与"从关系边推导出的状态"完全一致，且这个一致性查询可以**直接作为回归测试**：

```sql
SELECT m.id, m.status AS stored,
  CASE WHEN NOT EXISTS (SELECT 1 FROM memory_relations r
        WHERE r.to_memory_id=m.id AND r.kind='supersedes')
       THEN 'active' ELSE 'superseded' END AS derived
FROM memories m;
```

### 12.2 检索层验证通过

实测在 `memories` 表上同时建立 **HNSW（`vector_cosine_ops`）** 与 **GIN（`tsvector`）** 索引，并在**单条 SQL** 里完成语义 + 词法的 RRF 融合：

```text
memory_id | sem_rank | lex_rank | rrf_score
  m1      |    3     |    1     |  0.032266
  m3      |    2     |    2     |  0.032258
  m2      |    1     |          |  0.016393
```

**三条由此确定的结论：**

1. **RRF 完全可以在 Postgres 单条 SQL 里完成**，不需要额外的应用层融合服务，也不需要为了混合检索引入第二个数据库。
2. `tsvector` 用 `simple` 配置（不做词干化）对**中文场景更合适**——但要注意：**Postgres 原生全文检索对中文分词支持很弱**（`simple` 只是按空格/标点切分）。**如果记忆内容以中文为主，词法检索这一路需要认真处理**：可选方案是 `pg_trgm`（三元组，对中文较友好）、`zhparser` / `pg_jieba` 扩展，或把中文分词交给应用层后用 `tsvector` 的数组形式写入。**这是原方案没有提到、但在你的使用场景（中文为主）下必然会撞上的问题。**
3. 语义与词法两路的结果确实互补（上例中 `m2` 只有语义命中，`m1`/`m3` 靠词法提升），**验证了 §11 关于"不能只用 Vector Search"的判断**。

### 12.3 Embedding 模型选型（最后一个待定项）

2026 年的可选方案（MTEB 分数与价格来自第三方汇总，仅作量级参考）：

| 模型 | MTEB | 维度 | 价格 / 百万 token | 最大 token | 许可 |
|---|---|---|---|---|---|

#### ⚠️ 先纠正一个常见的评估误区：**成本在你这儿几乎不重要**

几乎所有 embedding 选型文章都在谈"十亿 token 规模下的成本"。**但 Memory Palace 是单用户的个人记忆系统**：假设积累 10,000 条记忆、每条平均 50 token，全量嵌入一次 = **50 万 token**。按上表最贵的 OpenAI large 算 = **约 $0.065，一次性**。就算换十次模型，总花费也不到一块钱。

**所以不要用成本来选。** 真正应该驱动决策的是三条：

1. **中文语义质量**——你的记忆内容以中文为主，而上表的 MTEB 主要是英文基准。
2. **隐私**——记忆是**最敏感的个人数据**。用云 API 意味着每一条私人记忆原文都会发送给 provider。
3. **维度**——直接影响存储与索引。3072 维相比 1024 维存储约 3 倍，而召回提升通常很小（large 与 Cohere 的 MTEB 只差 1.6 个点，维度却高 3 倍）。

#### 建议

| 取向 | 选择 | 理由 |
|---|---|---|
| **重视隐私（推荐先评估）** | **BGE-M3** 本地自托管 | MIT、1024 维、专为多语言设计、可完全离线。记忆原文永不离开本机，与"本地优先"的产品定位天然一致。代价是一次性跑通本地推理（`@huggingface/transformers` 4.3.0 或 Ollama） |
| 重视省事 | Cohere `embed-v4` | 多语言最好、1024 维，且 dense + sparse 一体——sparse 可直接喂给词法那一路，正好缓解下面提到的中文分词问题 |
| 重视便宜 | Google `text-embedding-005` | $0.005/M 且 768 维。注意 2048 token 上限，长 Experience 需先切分 |

**不推荐 `text-embedding-3-large`（3072 维）**：为 1.6 个 MTEB 点付出 3 倍存储，在 10 万级规模下是明显的过度配置。

#### 一条重要的工程含义

研究明确指出：**不同 provider 的 embedding 处于不同的数学空间、不可混用；换 provider 必须全量重嵌入。**

这**正面验证了开发计划 §3.1 里 `memory_embeddings` 按 `(memory_id, model)` 分行存储的设计**——它把"换模型"从一次停机迁移变成"后台渐进重嵌入 + 双模型并行 A/B"。**这是那个设计决策最大的实际回报，值得在 ADR-0001 里明确写下来。**

#### 中文词法检索方案（相关待定项）

Postgres 原生全文检索对**中文分词支持很弱**（`simple` 配置基本只按标点切分）。可选：

- **`pg_trgm`**（三元组，内置扩展、对中文较友好）——**建议先用它起步**，零额外依赖
- Cohere `embed-v4` 的 **sparse 向量**（若选它，可绕过分词问题）
- `zhparser` / `pg_jieba`（分词质量最好，但引入编译依赖，与"保持轻"冲突）

把它做成 `lexical` 端口的一个 adapter——**分词策略大概率要换，端口化后替换成本很低。**

> 这两项都**不阻塞 Phase 0/1**。Phase 1 建表时可以先用 `vector(1024)` 占位，因为换模型只需重新嵌入，不需要改表结构。

## 14. 被否决方案汇总

| 方案 | 否决理由 | 何时重新考虑 |
|---|---|---|
| Python 为主 | 双语言税；MCP 不同构；分析能力可只读 Postgres 获得 | 永不进入写路径 |
| Bun / Deno | 驱动锁定（`Bun.SQL`）；MCP 子进程路径未经充分验证 | 生态成熟且无锁定后 |
| `@modelcontextprotocol/sdk` (v1) | 已进入 legacy，仅 6 个月修复期 | 不适用（用 v2） |
| TS 版 FastMCP（社区） | 仍依赖 v1，与 v2 脱节 | 跟进 v2 后 |
| Prisma | 无法创建 pgvector 索引；抽象层对抗手写 SQL | 不适用 |
| SQLite + sqlite-vec | 放弃范围类型/窗口函数/并发写，bi-temporal 高度依赖 | 不适用 |
| PGlite（当前） | MCP stdio 每会话一进程 → 多实例写同一文件会损坏 | **改为单长驻 HTTP 进程时** |
| Qdrant / Chroma / Weaviate | 第二个存储系统 = 双倍一致性/运维成本，收益仅"快一点" | 向量检索成为实测瓶颈时 |
| Neo4j / Graph DB | 部署/同步/查询/运维四重复杂度（同意 §18） | 关系检索成为**实测**瓶颈时 |
| LangChain.js | 抽象泄漏、升级痛苦；已用显式 pipeline 更清楚地解决 | 不适用 |
| Turborepo | 8 包单人规模下配置复杂度 > 收益 | 包数量或 CI 时间显著增长后 |
| Node 原生 TS 直跑 | 不支持 node_modules 内 TS，与 pnpm workspace 冲突 | 但**保留** erasable syntax 约束以便将来启用 |
